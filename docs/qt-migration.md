# The wxWidgets → Qt migration

This fork builds KiCad without wxWidgets: the core and `kicad-cli` run on a small reimplementation
of the wxBase API (`kiwx`), and the whole GUI (project manager, editors, viewers, dialogs) runs on
Qt 6. The goal is to keep the upstream KiCad sources compiling **unchanged** wherever possible, so
that the fork can keep following upstream, and to replace only what is toolkit specific.

This page describes how the port is organised, what works, what is still missing, how to build
it on each platform and how CI checks it. It reflects the state of the `wx-free-core-upstream`
branch.

## Overview

```
                 upstream KiCad sources (common/, pcbnew/, eeschema/, ...)
                                  │ compiled unchanged
          ┌───────────────────────┴────────────────────────┐
          │                                                │
  core + kicad-cli                                  GUI code (frames, tools,
  (model, I/O, plotting, DRC/ERC...)                dialogs, panels, widgets)
          │                                                │
          ▼                                                ▼
   libs/kiwx  (wxBase API:                       qt/include  (Qt versions of the GUI
   wxString, wxFileName, wxConfig,               base classes: EDA_BASE_FRAME,
   wxDateTime, wxRegEx, wxLog...)                EDA_DRAW_FRAME, canvas, KIWAY...)
                                                 qt/wxcompat (wxWindow, wxDialog, wxGrid,
                                                 wxDataViewCtrl, wxAui*, wxStyledTextCtrl...
                                                 as Qt widgets)
          │                                                │
          └──────────────────────┬─────────────────────────┘
                                 ▼
                         Qt 6 (Widgets, Network, PrintSupport, OpenGL)
```

Two layers do the work:

1. **kiwx** (`libs/kiwx`) provides the non-GUI part of wxWidgets that the KiCad core uses.
   With it, the core libraries and `kicad-cli` build and run with no wxWidgets at all.
2. **The Qt shell** (`qt/`) provides the GUI. It has hand-written Qt versions of KiCad's GUI base
   classes (`qt/include`, `qt/common`) and a compatibility layer, **wxcompat**
   (`qt/wxcompat`), that implements the subset of the wx GUI API the upstream dialogs, panels and
   tools use, on top of Qt widgets. The upstream editor sources are then compiled against these
   headers instead of the wxWidgets ones.

## Architecture

### Build options

Three CMake options in the top-level `CMakeLists.txt` select the build:

| Option | Default | Effect |
| --- | --- | --- |
| `KICAD_WX_FREE` | `OFF` | Build the core and `kicad-cli` on kiwx instead of wxWidgets (`cmake/WxFree.cmake`). Defines the `KICAD_WX_FREE` macro and forces `KICAD_SCRIPTING_WXPYTHON=OFF` and `KICAD_UPDATE_CHECK=OFF`. |
| `KICAD_QT_SHELL` | `OFF` | With `KICAD_WX_FREE`, also build the Qt GUI (`add_subdirectory( qt )`): `kicad-qt` and the Qt KIFACEs. |
| `KICAD_HEADLESS_ONLY` | `OFF` | With `KICAD_WX_FREE` and without `KICAD_QT_SHELL`: `kicad-cli` with no OpenGL, GLU, Wayland, Poppler, spnav or libsecret. See [Headless core](#headless-core-kicad-cli-only). |

With both options off the tree is ordinary upstream KiCad and builds against wxWidgets as usual.

`cmake/WxFree.cmake` replaces the wxWidgets lookup (`wxWidgets_LIBRARIES` points to `kiwx`, the
kiwx headers come first on the include path) and restricts the build to the targets listed in
`cmake/WxFreeSources.cmake` (generated by `tools/wxfree_sources.py`) plus the ones the Qt tree adds
to the `KICAD_WX_FREE_KEPT_TARGETS` property. Every other upstream target is left out of the build;
its install rules are tolerated (missing files are optional).

Shared code that needs a Qt-only branch tests `#ifdef KICAD_WX_FREE`.

### kiwx: the wxBase API without wxWidgets

`libs/kiwx` implements, under the wx names, the part of wxBase 3.2 the core uses: strings and
formatting, `wxFileName`/file functions, `wxDateTime`, `wxConfig`/`wxFileConfig`, archives
(zip), base64, `wxAny`, regular expressions (PCRE2, 16-bit code units on Windows and 32-bit
elsewhere, as wxWidgets), translations (`wxLocale`/`intl`), dynamic libraries, the app object and
logging. Its headers live in `libs/kiwx/include/wx` and shadow the wxWidgets ones. It depends only
on Expat, zlib, PCRE2 and threads.

kiwx does **not** define any wx port macro: `__WXMSW__`, `__WXGTK__` and `__WXMAC__` are never set
in this build. See [Quirks and pitfalls](#quirks-and-pitfalls).

### The qt/ tree

| Directory | Contents |
| --- | --- |
| `qt/CMakeLists.txt` | Finds Qt 6 (`Widgets Network PrintSupport`, at least 6.2), defines the fbp generation helpers, adds the subdirectories and the kept targets. |
| `qt/include` | Qt versions of the GUI headers of KiCad (`eda_base_frame.h`, `eda_draw_frame.h`, `class_draw_panel_gal.h`, `kiway.h`, `kiway_player.h`, `dialog_shim.h`, `tool/`, `widgets/`, `kiplatform/`...). They come **before** the upstream include directories, so upstream sources include them unchanged. |
| `qt/common` | `libkiqt` (shared library: icons/bitmap store, cursors, message dialogs, event loop, Cairo and OpenGL GAL canvases, documents, property panel, KIWAY) and `libkiqt_common` (static, linked into every Qt KIFACE: the upstream tool framework on the Qt frames, canvas, menus and base dialogs). |
| `qt/wxcompat` | The wxWidgets GUI compatibility layer (see below): about 145 headers in `qt/wxcompat/include/wx` and the `kiwx_*.cpp` implementations. |
| `qt/libs/kiplatform` | Qt implementations of `KIPLATFORM::UI` and printing. |
| `qt/pcbnew`, `qt/eeschema`, `qt/cvpcb`, `qt/gerbview`, `qt/pagelayout_editor`, `qt/pcb_calculator`, `qt/bitmap2component`, `qt/scripting`, `qt/3d-viewer` | One directory per application: compiles the upstream sources of that application's KIFACE against the Qt headers and wxcompat, plus a few Qt-specific replacements (`*_qt.cpp`). |
| `qt/kicad` | `kicad-qt`, the project manager program (`KICAD_MANAGER_FRAME` on wxcompat), its Windows resource file and `manager.cmake`. |
| `qt/qa` | GUI tests of the Qt build (see [CI](#continuous-integration)). |
| `qt/tools` | `fbp2qt.py` (dialog generator), `check_generated_deps.py` (build-order check), the vcpkg overlay triplet and the Windows NSIS installer script (`qt/tools/windows/kicad-qt.nsi`). |

### wxcompat: the wx GUI API on Qt widgets

`qt/wxcompat` lets upstream dialog, panel and tool code compile against Qt. The rules, from
`qt/wxcompat/include/wx/kiwx_gui.h`:

- **Each control is its Qt widget.** `wxCheckBox` derives from `QCheckBox`, `wxTextCtrl` from a
  Qt text widget, and so on, through the `wxWindowCompat<QT>` template (`kiwx_window.h`). The Qt
  side of the object is configured with the Qt API (by the generated dialog bases), and the
  upstream code uses the wx API on the same object.
- **Only what KiCad uses is there.** It is not a wxWidgets port: methods exist because some KiCad
  source calls them, and they behave as Qt does (layouts instead of sizers, no static event
  tables).
- **Events.** `wxEvtHandler`, `Bind()`/`Unbind()`, `QueueEvent()`/`CallAfter()` and the usual
  event types are implemented in `kiwx_events.h`. Command events do **not** bubble up to parent
  windows generically: `ProcessChainCompat()` only walks the handlers pushed on the same object.
  Controls whose events KiCad catches on a parent forward them explicitly (for example
  `wxPropertyGrid` to its manager).

Implemented families include: basic controls, books/notebooks, `wxGrid` (`kiwx_grid.cpp`),
`wxDataViewCtrl` and models (`kiwx_dataview.cpp`), `wxTreeCtrl`/`wxTreeListCtrl`,
`wxListCtrl`, `wxPropertyGrid`, AUI managers and notebooks on `QMainWindow` docks
(`kiwx_aui.cpp`), `wxStyledTextCtrl` (`kiwx_stc.cpp`), menus, status bar, pickers (colour, file,
dir, font), file/message dialogs, clipboard, DC/GDI drawing on `QPainter` (`kiwx_gdi.cpp`),
printing, validators, wizards and `wxWebView` (`kiwx_webview.cpp`).

**The web view.** `wxWebView` delegates to a backend (`wx/kiwx_webview_backend.h`), the web engine
of the platform as in upstream wx: **Qt WebEngine** on Linux (`kiwx_webview_qtwebengine.cpp`,
option `KICAD_QT_WEBENGINE`, from the distribution; it avoids pulling GTK in through WebKitGTK),
**WKWebView** on macOS (`kiwx_webview_wkwebview.mm`, built with ARC) and **WebView2** on Windows
(`kiwx_webview_webview2.cpp`, vcpkg port `webview2`; the Edge runtime of Windows, no Chromium in
the package). Each one implements navigation, new-window, title and error events, `RunScript()`
and `RunScriptAsync()`, script message handlers (`window.<name>.postMessage()` in the page,
`wxEVT_WEBVIEW_SCRIPT_MESSAGE_RECEIVED` on the view), user scripts and the cookies used by
`KIPLATFORM::WEBVIEW` (`qt/libs/kiplatform/webview.cpp`). Without an engine the view falls back
to a `QTextBrowser` (local HTML, no scripts). The web view events reach the parents of the view
explicitly (`wxWebView::SendEventCompat()`). The **Remote Symbols** panel of the schematic editor
is the upstream `eeschema/widgets/panel_remote_symbol.cpp`; its OAuth loopback server has a Qt
implementation (`qt/common/oauth_loopback_server_qt.cpp`, a `QTcpServer`).

### Dialogs: fbp2qt

Upstream dialogs are designed in wxFormBuilder (`*.fbp`) and their `*_base.cpp/.h` are generated
code that calls wxWidgets directly. In the Qt build these bases are regenerated at build time by
`qt/tools/fbp2qt.py`, which reads the same `.fbp` file and writes a class with the same name and
the same members, using Qt widgets and Qt layouts for the sizers. Two modes are available from
CMake:

- `kiqt_generate_fbp()`: plain Qt bases. The derived class (the dialog logic) is written for Qt by
  hand. Used by a few core dialogs.
- `kiqt_generate_fbp_compat()` (`--wx-compat`): the members are wxcompat controls and the events
  are wx events. The **upstream** derived class then compiles unchanged. This is how most
  dialogs and panels of the editors are built.

The generated files go to `${CMAKE_BINARY_DIR}/qt/fbp/<source dir>` and that directory is put
before the upstream one on the include path, so `#include <dialogs/dialog_foo_base.h>` picks the
Qt version. `qt/tools/check_generated_deps.py` verifies, after a build, that every generated
header is ordered before the objects that include it (a clean parallel build could otherwise
compile them first).

### Frames, canvas and tools

- `EDA_BASE_FRAME` is a `QMainWindow`. AUI panes become `QDockWidget`s (with nested and tabbed
  docks), menus and toolbars are Qt menus/toolbars driven by the upstream `ACTION_MANAGER` and
  `TOOL_MANAGER`.
- The drawing canvas (`EDA_DRAW_PANEL_GAL`) supports both GAL backends:
  - **Cairo** (`qt/common/qt_cairo_gal.cpp`), drawn into an image painted by the widget.
  - **OpenGL** (`qt/common/gal/opengl_gal_qt.cpp`, `hidpi_gl_canvas.cpp`): the upstream OpenGL
    GAL on a `QWindow` with an OpenGL surface, embedded with `QWidget::createWindowContainer()`.
    The window is frameless and created after being embedded (otherwise Windows kept the margins
    of a top-level frame and drew an offset image with black bands), and it never takes keyboard
    focus (keys go to the canvas widget, so two open editors do not fight over activation).
    HiDPI and fractional scales (e.g. 125%) are handled by rounding as Qt sizes native windows.
- The 3D viewer (`qt/3d-viewer`) runs the upstream OpenGL renderer and ray tracer in a Qt
  OpenGL window.
- Library trees (`qt/common/lib_tree_model_adapter_qt.cpp`) back the symbol/footprint choosers
  and the editor panes with a Qt item model.
- The property panel (`qt/common/property_panel.cpp`, `qt/common/properties`) is Qt native and
  driven by the upstream `PROPERTY_MANAGER`.

### KIFACEs and the kicad-qt program

As upstream, each application is a KIFACE loaded by KIWAY. The Qt build produces:

| KIFACE | Contents |
| --- | --- |
| `_pcbnew_qtgui.kiface` | PCB editor, footprint editor/viewer, 3D viewer, router, Python bindings |
| `_eeschema_qtgui.kiface` | Schematic editor, symbol editor/viewer, simulator |
| `_cvpcb_qtgui.kiface` | Footprint assignment tool |
| `_gerbview_qtgui.kiface` | Gerber viewer |
| `_pl_editor_qtgui.kiface` | Drawing sheet editor |
| `_pcb_calculator_qtgui.kiface` | Calculator tools |
| `_bitmap2component_qtgui.kiface` | Image converter |
| `_kipython_qtgui.kiface` | Python console (a Qt console instead of the wxPython shell) |
| `_pcbnew_qt.kiface`, `_eeschema_qt.kiface` | Headless KIFACEs with the board/schematic documents |

`kicad-qt` (`qt/kicad`) is the project manager (`KICAD_MANAGER_FRAME`, including the plugin and
content manager dialogs) and loads the editors from these KIFACEs. On Windows it is a GUI
subsystem program with the KiCad icon. `kicad-cli` is the upstream one, built on kiwx.

The legacy `pcbnew` Python module (SWIG) is generated from the same interface files as upstream
and built on kiwx; it is installed next to the KIFACEs. wxPython is not available.

## What is ported

All the main applications start and work from the Qt project manager:

- Project manager (`kicad-qt`) with its project tree, launcher, start wizard, plugin and content
  manager dialogs.
- Schematic editor, symbol editor, symbol viewer and chooser, simulator.
- PCB editor (including the interactive router), footprint editor and viewer, 3D viewer
  (OpenGL and ray tracing).
- Footprint assignment tool (CvPCB), Gerber viewer, drawing sheet editor, calculator tools,
  image converter, Python console.
- The upstream dialogs and panels of these tools, compiled unchanged on wxcompat through
  `fbp2qt --wx-compat`.
- Both GAL backends (Cairo and OpenGL), printing, the clipboard, translations, dark theme
  detection, HiDPI and fractional scaling.
- Embedded images in schematics and drawing sheets: in addition to the PNG/JPEG decoders of the
  core, `RegisterQtImageDecoder()` (`qt/common/raster_image_qt.cpp`) lets `RASTER_IMAGE` decode any
  format Qt's image plugins read (BMP, GIF, CMYK JPEG...).
- The layout of the docks of each frame, saved with its settings and restored
  (`EDA_BASE_FRAME::RestoreAuiLayout()`).
- Drag and drop in `wxDataViewCtrl` (e.g. zone priorities in the zone manager) and columns of
  `wxGrid` moved by dragging their labels (e.g. the symbol fields table).
- The preview popup of the hovered symbol or footprint in the library trees.
- Web views with a real engine per platform and the **Remote Symbols** panel (see
  [wxcompat](#wxcompat-the-wx-gui-api-on-qt-widgets)).
- Packaging: Windows installer and portable zip, macOS `.dmg` (see [CI](#continuous-integration)).

## Known gaps

These are known differences from the wxWidgets build on `wx-free-core-upstream`:

| Area | Status |
| --- | --- |
| **Image formats** | TIFF and WebP images cannot be decoded: Qt reads them only through the `qtimageformats` module, which is not in the Windows vcpkg `qt` feature (`vcpkg.json`: `qtbase`, `libpng`, `libjpeg-turbo`, `webview2`) and not installed by the Linux/macOS CI. |
| **Styled text** | `wxStyledTextCtrl` is a plain Qt text editor: lexer-based syntax highlighting (e.g. in the custom rules editor) is not applied. |
| **3D models** | The 3D model loader plugins (`plugins/3d`) are not part of the wx-free target set, so component 3D models are not loaded in the 3D viewer. |
| **wxPython** | Not available (`KICAD_SCRIPTING_WXPYTHON` is forced off). Action plugins that use wxPython dialogs do not work; the `pcbnew` module itself is available. |
| **Update check** | Disabled (`KICAD_UPDATE_CHECK` is forced off). |
| **Linux package** | CI checks a staged install but does not publish a Linux package. |

## Building

The Qt build needs Qt 6.2 or newer (Widgets, Network, PrintSupport) plus the usual KiCad
dependencies, but **no wxWidgets and no wxPython**. The authoritative recipes are the CI workflows
in `.github/workflows/qt-*.yml`; the commands below are taken from them.

Common CMake flags:

```
-DKICAD_WX_FREE=ON -DKICAD_QT_SHELL=ON -DKICAD_USE_PCH=OFF
```

Add `-DKICAD_BUILD_QA_TESTS=ON` and the `qa_qt_*` targets to build the GUI tests.

### Linux

Tested on Ubuntu 24.04 (its Qt is 6.4).

```sh
sudo apt-get install -y --no-install-recommends \
  build-essential cmake ninja-build ccache gettext swig \
  qt6-base-dev qt6-base-dev-tools qt6-qpa-plugins qt6-wayland \
  qt6-webengine-dev qt6-webchannel-dev \
  libboost-all-dev libglm-dev libglew-dev libgl-dev libglu1-mesa-dev libegl-dev \
  libcairo2-dev libpixman-1-dev libharfbuzz-dev libfontconfig-dev libfreetype-dev \
  libcurl4-openssl-dev libgit2-dev libsecret-1-dev libnng-dev unixodbc-dev \
  libngspice0-dev libprotobuf-dev protobuf-compiler libzstd-dev zlib1g-dev \
  libocct-data-exchange-dev libocct-foundation-dev libocct-modeling-algorithms-dev \
  libocct-modeling-data-dev libocct-ocaf-dev libocct-visualization-dev \
  libpython3-dev python3-dev pybind11-dev libspnav-dev libzint-dev \
  libpoppler-dev libpoppler-glib-dev libsqlite3-dev libeigen3-dev \
  pkg-config libglib2.0-dev libwayland-dev wayland-protocols libpcre2-dev \
  libexpat1-dev libpng-dev libjpeg-dev libssl-dev libgtk-3-dev

cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release -DCMAKE_INSTALL_PREFIX=/usr \
```

### macOS

Tested on macOS 15 (Apple Silicon) with Homebrew libraries:

```sh
brew install ninja ccache swig coreutils pkgconf gettext \
  qt boost glm glew cairo pixman harfbuzz fontconfig freetype \
  libgit2 nng unixodbc libngspice protobuf zstd opencascade \
  python@3.13 pybind11 zint poppler sqlite eigen glib openssl@3 curl

BREW=$(brew --prefix)
PY=$(brew --prefix python@3.13)/bin/python3.13
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release \
  -DCMAKE_OSX_DEPLOYMENT_TARGET=13.0 \
  -DCMAKE_PREFIX_PATH="$BREW;$(brew --prefix qt);$(brew --prefix openssl@3);$(brew --prefix curl)" \
  -DPython3_EXECUTABLE=$PY -DPYTHON_EXECUTABLE=$PY \
  -DNGSPICE_LIB_NAME=ngspice -DOCC_INCLUDE_DIR=$BREW/include/opencascade \
  -DKICAD_WX_FREE=ON -DKICAD_QT_SHELL=ON -DKICAD_USE_PCH=OFF \

```

The CI also passes `PYTHON_INCLUDE_DIR`, `PYTHON_LIBRARY` and `PYTHON_FRAMEWORK` so that the
Homebrew Python is used rather than the system one. `KiCad.app` is not produced by CMake: the
"Package" step of `qt-macos.yml` assembles it (programs and KIFACEs in `Contents/MacOS`, data and
libraries in `Contents/SharedSupport`, Python framework, `macdeployqt` for Qt and Homebrew
libraries, run-path rewriting and an ad-hoc signature). The bundle is not notarized.

### Windows

MSVC (Visual Studio 2022) with vcpkg. The manifest has a dedicated `qt` feature; the overlay
triplet `x64-windows-release` (`qt/tools/vcpkg-triplets`) builds release-only libraries.

```powershell
vcpkg install --x-manifest-root=. --x-no-default-features --x-feature=qt `

cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release `

  -DVCPKG_OVERLAY_TRIPLETS="qt\tools\vcpkg-triplets" `
  -DVCPKG_MANIFEST_NO_DEFAULT_FEATURES=ON -DVCPKG_MANIFEST_FEATURES=qt `

cmake --build build
```

Run it from a "Developer PowerShell for VS". The package layout (`bin`, `share\kicad`,
`qt.conf` with the Qt plugins in `bin\qtplugins`, the vcpkg DLLs, Python in `bin\Lib`) is
produced by the "Package" step of `qt-windows.yml`; the installer is built with NSIS from
`qt/tools/windows/kicad-qt.nsi`.

### Running from the build tree

Set `KICAD_RUN_FROM_BUILD_DIR=1` and start `build/kicad/kicad-qt`: KIWAY then finds the KIFACEs
and the resources (images archive, schemas) in the build tree, as with the upstream build.

### Headless core: kicad-cli only

The core (data model, file I/O, DRC/ERC, plotters, exporters) does not depend on the GUI:
`kicad-cli`, `_pcbnew_cli.kiface` and `_eeschema_cli.kiface` link kiwx and the model libraries
(`kicommon_model`, `gal_model`, `pcbcommon`...), never Qt, wxWidgets or wxcompat, and they run
with no display. They are what a server or a CI pipeline needs for batch DRC/ERC and the
fabrication exports.

`-DKICAD_WX_FREE=ON` alone (without `KICAD_QT_SHELL`) builds only them. Add
`-DKICAD_HEADLESS_ONLY=ON` to also leave out what the desktop needs:

| Dependency | Without `KICAD_HEADLESS_ONLY` | With it |
| --- | --- | --- |
| OpenGL, GLU | `find_package( OpenGL REQUIRED )`; `libGLU` linked by `_pcbnew_cli.kiface` (the GLU tessellator of the VRML export, `utils/idftools/vrml_layer.cpp`) | Not searched. The tessellator is built from `thirdparty/libtess` (the libtess of Mesa GLU 9.0.2, SGI Free B 2.0) as the static `kitess`; `include/kicad_gl/kiglu.h` includes `<kitess/glu.h>`. glad gives only the GL types (no GLX/EGL sources). |
| Wayland | `KICAD_WAYLAND=ON` on Linux | Forced `OFF` |
| spnav (3D mouse) | Required on Linux | Not searched |
| Poppler (printing) | Required on Linux by `libs/kiplatform` | Not searched |
| libsecret (keyring) | Linked by `kiplatform_core` | `os/unix/secrets_none.cpp`: no secret is stored or found (git credentials and OAuth tokens are not remembered) |

Build and run on Linux (Ubuntu 24.04 packages):

```sh
sudo apt-get install build-essential cmake ninja-build gettext swig \
  libboost-all-dev libglm-dev \
  libcairo2-dev libpixman-1-dev libharfbuzz-dev libfontconfig-dev libfreetype-dev \
  libcurl4-openssl-dev libgit2-dev libnng-dev unixodbc-dev \
  libngspice0-dev libprotobuf-dev protobuf-compiler libzstd-dev zlib1g-dev \
  libocct-data-exchange-dev libocct-foundation-dev libocct-modeling-algorithms-dev \
  libocct-modeling-data-dev libocct-ocaf-dev \
  libpython3-dev python3-dev pybind11-dev libzint-dev \
  libsqlite3-dev libeigen3-dev pkg-config libglib2.0-dev libpcre2-dev \
  libexpat1-dev libpng-dev libjpeg-dev libssl-dev

cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release \
  -DKICAD_WX_FREE=ON -DKICAD_HEADLESS_ONLY=ON -DKICAD_USE_PCH=OFF
cmake --build build          # about 1050 steps, 20-30 minutes on four cores

# No DISPLAY needed
KICAD_RUN_FROM_BUILD_DIR=1 build/kicad/kicad-cli pcb drc --format json -o drc.json board.kicad_pcb
```

What is left, none of it needing a display:

- The distribution libraries can still pull in X11 or GL **indirectly**: Ubuntu's Cairo links
  `libX11`/`libxcb` (its Xlib surface is never used, Cairo draws into memory), and the OCCT
  `-dev` packages depend on the GL headers. The programs load these libraries but open no
  connection. A static or custom Cairo/OCCT removes them.
- GLib/GIO (`kiplatform_core`) and Fontconfig/FreeType/HarfBuzz (the outline fonts) are used by
  the core; they are not GUI libraries.
- Python (`PythonLibs`) and ngspice are still required at configure time, as in upstream.
- A fresh home has no global library tables. `kicad-cli` works without them (the boards and
  schematics carry their footprints and symbols) and no longer prints an assert about them
  (`LIBRARY_MANAGER::LoadGlobalTables`).
- `KICAD_HEADLESS_ONLY` is built and tested on Linux only. On macOS, `kiplatform_core` links
  the system frameworks (Cocoa/AppKit) as upstream does.

CI checks it on every Linux run (job `headless` of `qt-linux.yml`, see below).

## Continuous integration

Three workflows build and test the Qt build:

| Workflow | Runner | Toolchain | Artifacts |
| --- | --- | --- | --- |
| `qt-linux.yml` — *Qt build (Linux)* | `ubuntu-24.04` | GCC, distribution Qt | the AppImage (`kicad-qt-*-x86_64.AppImage`), QA screenshots |
| `qt-macos.yml` — *Qt build (macOS)* | `macos-15` (arm64) | Apple Clang, Homebrew Qt | the disk image (`kicad-qt-*.dmg`), screenshots, crash reports |
| `qt-windows.yml` — *Qt build (Windows)* | `windows-2022` | MSVC, vcpkg Qt | the installer (`kicad-qt-*.exe`) and the portable zip (`kicad-qt-*-portable.zip`) |

The packages are uploaded with `actions/upload-artifact@v7` and `archive: false`: the artifact
is the file itself, named as the file, not a zip around it (the other artifacts stay zipped).

**Nightly release.** After a green run of a push to `wx-free-core-upstream`, the Linux, Windows
and macOS workflows publish their packages on the `nightly` pre-release of GitHub (Releases, on the
home page of the repository) with `qt/tools/ci/nightly_release.sh`: the tag moves to the commit
and the assets of the platform are replaced. Linux publishes an AppImage, made by
`qt/tools/ci/appimage.sh` with linuxdeploy and its Qt plugin from the staged install and the KiCad
libraries (symbols, footprints, template); its `AppRun` sets `KICAD_STOCK_DATA_HOME` and runs
`kicad-qt` (or `kicad-cli`, as `<image> kicad-cli ...`).

**Qt versions.** macOS takes the Qt of Homebrew, Windows the `qtbase` of vcpkg (pinned with an
override in `vcpkg.json`, 6.11.3, the other libraries stay at the baseline), Linux the Qt of the
distribution (6.4 on Ubuntu 24.04).

**Triggers.** They run on push to `wx-free-core-upstream` and on manual dispatch
(`workflow_dispatch`); other branches only get CI when dispatched. Pushes that change only
`**.md`, `demos/**` or `translation/**` are ignored. A run for the same ref cancels the previous
one.

**What each run does.**

1. Build everything plus the GUI tests (`qa_qt_pcbnew_frames`, `qa_qt_eeschema_frames`,
   `qa_qt_tool_framework`, `qa_qt_3d_viewer`, `qa_qt_kicad_shell`), with ccache.
2. Linux only: `check_generated_deps.py` checks the order of the generated headers.
3. Run the GUI tests: the PCB editor frames, the tool framework on the canvas, the 3D viewer, the
   schematic editor frames, and the whole `kicad-qt` shell driven by synthesized input (it opens
   a board and a schematic, the editors and tools, and takes a screenshot). Linux runs them under
   Xvfb and gdb (stack traces of all threads on a crash). Linux also re-runs the shell in Italian
   at 125% scaling (decimal comma, translated strings, fractional icon scaling) and the
   OpenGL canvas at 125% with Mesa in software. Windows runs them with the llvmpipe
   `opengl32.dll` of mesa-dist-win next to the programs (the runner has no GPU), including the
   OpenGL canvas at 125%.
4. Package and test the package **in isolation**:
   - Linux: staged `cmake --install` and an `ldd` check that no library is missing.
   - macOS: build `KiCad.app` with the symbol, footprint and template libraries (cloned from
     GitLab at the matching tag), make a `.dmg`, copy `KiCad.app` out of it and run `kicad-cli` exports and the shell test from
     the copy (failing on any Fontconfig error).
   - Windows: build the package with the same libraries, copy it away from the build tree with
     the build prefix hidden, and run the shell test there; build the NSIS installer, install it
     silently, check the registry entry and the Start menu shortcut, start the installed KiCad;
     finally zip the package as the **portable** version
     (`kicad-qt-<version>-x86_64-portable.zip`, with a `KiCad.cmd` launcher) and check that the
     extracted zip runs `kicad-cli` without the build `PATH`.

**Headless job (Linux).** `qt-linux.yml` also has the `headless` job: it installs no Qt, GLEW,
GLU, GTK, Wayland, Poppler, spnav or libsecret package, configures with
`KICAD_HEADLESS_ONLY=ON` and the finds of OpenGL, Poppler, Wayland and spnav disabled (so the
configuration fails if one of them becomes required again), and builds. Then
`qt/tools/ci/check_headless.py` checks that no program or library of the build links a GUI,
GL, X11/xcb, Wayland, GTK, Poppler, spnav, libsecret, Qt or wx library and that no object
includes their headers (`ninja -t deps`), and `qt/tools/ci/headless_cli_test.sh` runs
`kicad-cli` with no `DISPLAY`/`WAYLAND_DISPLAY` and an empty home: version, DRC and ERC (JSON
reports, non-empty), Gerbers, drill, positions, SVG, STEP, VRML (the `kitess` tessellator),
3D render, schematic PDF, netlist and BOM on the `video` and `pic_programmer` demos, failing on
any non-zero exit code, missing output or assert. The outputs are uploaded as
`headless-cli-outputs`.

**Duration.** Linux and macOS take about 80 minutes with a warm cache. Windows has two jobs (the
vcpkg libraries, cached by the hash of `vcpkg.json`, `vcpkg-configuration.json` and the triplets;
then KiCad) and takes about three hours when the vcpkg cache is cold.

**Integration.** Pull requests are not used: `.github/workflows/lockdown.yml`, inherited from the
KiCad mirror, closes and locks every PR. Work happens on branches; the three workflows are
dispatched on the branch, and once they are green on Linux, Windows and macOS the main branch
is fast-forwarded to it (rebased and re-tested first if a fast-forward is not possible).

## Quirks and pitfalls

- **No wx port macros.** `__WXMSW__`, `__WXGTK__` and `__WXMAC__` are never defined in the Qt
  build. Upstream code under `#ifdef __WXMSW__` silently does not run on Windows. Use `_WIN32`,
  `__APPLE__` or `__linux__` for platform checks, or `KICAD_WX_FREE` for Qt-only code.
  For example, `common/paths.cpp` defines `KICAD_WINDOWS_LAYOUT` for
  `__WXMSW__ || ( _WIN32 && KICAD_WX_FREE )`.
- **Data paths on Windows / `KICAD_STOCK_DATA_HOME`.** Before `KICAD_WINDOWS_LAYOUT` was
  introduced, the Windows Qt build located its stock data through the compile-time
  `KICAD_DATA` path, i.e. the install prefix on the CI machine. Packages then showed `?` icons and
  missing data on any other computer, and the workaround was to set
  `KICAD_STOCK_DATA_HOME=<package>\share\kicad`. Current packages find `share\kicad` next to
  `bin` by themselves, so the variable is **no longer needed** (it is still honoured as an
  override). The Windows CI hides the build prefix while it tests the package so that this kind
  of regression is caught.
- **macOS data.** On macOS the stock data is found in the bundle (`Contents/SharedSupport`, via
  `PATHS::GetQtBundleContentsPath()`).
- **Native windows.** Do not call `QWidget::winId()` on a widget that might not have a native
  window yet: it sets `Qt::WA_NativeWindow` and Qt then makes the widget's siblings and ancestors
  native too. On Windows this has turned the toolbars, docks and central widget of the PCB editor
  into native windows that covered the OpenGL canvas (black canvas). Prefer
  `internalWinId()`/`windowHandle()` when only an existing handle is needed.
- **The OpenGL canvas is a separate native window** inside a `QWindowContainer`. Anything that
  makes Qt recreate the native window of a frame destroys the OpenGL window of its canvases;
  keep this in mind when adding native child widgets (web views, video, etc.) to an editor frame.
- **Qt WebEngine before Qt 6.7 (Ubuntu 24.04 has 6.4).** The first web view shown in a frame
  needs RHI (OpenGL) composition, so Qt destroys and recreates the frame's native window; before
  Qt 6.7 it does so without moving the windows of the `QWindowContainer`s aside, so the OpenGL
  window of the canvas is destroyed with it and the next move of the frame crashes in
  `QWindowContainer::parentWasMoved()`. On those versions `kiwx_webview_qtwebengine.cpp` sets
  `QT_WIDGETS_RHI=1` and `QT_WIDGETS_RHI_BACKEND=opengl` when the library is loaded (unless the
  environment already sets them), so every window is composed with OpenGL from the start and none
  is recreated. Running Qt WebEngine as root (containers) needs `QTWEBENGINE_DISABLE_SANDBOX=1`;
  the Linux CI sets it for the GUI tests because the runners do not allow Chromium's sandbox.
- **Event propagation.** As noted above, wxcompat command events do not bubble to parents. If
  upstream code binds a control's event on a dialog or frame, check that the control forwards it.
- **Frames are not deleted on close by Qt** (`WA_DeleteOnClose` is off): KiCad's own lifecycle
  (KIWAY) deletes them, as with wxWidgets. On macOS the dock animations and the toolbar/dock
  layout are torn down before a frame is deleted to avoid crashes in Qt's layout code.
- **Python and Qt keywords.** `Python.h` has struct members named like Qt keywords (`slots`); the
  GUI libraries whose sources include it are compiled with `QT_NO_KEYWORDS` (see
  `qt/*/CMakeLists.txt`), so Qt code there must use `Q_SLOTS`/`Q_SIGNALS`/`Q_EMIT`.
- **Generated headers.** Each fbp-generated header must be a dependency of the objects that
  include it; run `python3 qt/tools/check_generated_deps.py build` after adding dialogs.
